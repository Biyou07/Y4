1. Experimental Results & Step Analysis
Step 1 — Parity Bit (Even/Odd)
We implement byte-wise even parity by adding 1 parity bit to each 8-bit byte so that the total number of 1s in the 9-bit word is even. We transmit a 16-byte text payload across a BSC channel with p = 0.02.

Quick Test Output: Parity check passed: False (errors introduced by BSC are caught).

Observation on Even Errors: Parity only checks if the total count of 1s is even or odd. If 1 bit flips, parity changes and the error is detected. But if 2 bits flip in the same byte, the total count of 1s changes by +2, -2, or 0; the total remains even, so the check passes and the errors go completely undetected. In general, parity misses any even number of bit errors.

Step 2 — Simple Checksums (8-Bit Modular & 16-Bit Ones' Complement)
We implement two arithmetic checksums: (1) 8-Bit Modular Sum: Adds all bytes modulo 256 (sum(payload) & 0xFF) and appends the 1-byte sum. (2) 16-Bit Ones' Complement Checksum (Internet style): Adds 16-bit words with end-around carry and appends the inverted sum ((~s) & 0xFFFF).

Observation on Checksum Weakness: Checksums simply add numbers together, which leads to common misses: (1) Compensating errors: If one byte increases by an amount (+1) and another byte decreases by that same amount (-1), the errors cancel out and the sum stays identical. (2) Order doesn't matter: Swapping two bytes preserves the sum. Adding zeros or flipping between +0 (0x0000) and -0 (0xFFFF) also goes undetected.

Step 3 — Cyclic Redundancy Check (CRC-8 & CRC-16)
We implement a bitwise CRC engine using polynomial division over GF(2):
• CRC-8: Generator polynomial G(x) = x^8 + x^2 + x + 1 (0x07).
• CRC-16-CCITT: Generator polynomial G(x) = x^16 + x^12 + x^5 + 1 (0x1021, init 0xFFFF).

Key Detection Capabilities:
• Single and double bit errors: The math is designed so that 1-bit and 2-bit error patterns never divide evenly into the generator polynomial, so they are always detected.
• Any odd number of errors: Caught because the polynomial has (x + 1) as a factor.
• Burst errors: Any burst of errors up to the degree of the polynomial (up to 8 bits for CRC-8, up to 16 bits for CRC-16) is 100% guaranteed to be detected.

Comparing the Methods & Interpreting Results

1. Under Random Bit Errors (BSC):
• At low error rate (p = 0.001), about 35% of frames are clean and 65% have errors. Parity catches almost all errors (0.37% undetected), failing only when 2 bits flip in the same byte. CS8 has the highest undetected rate (~2.2%) because random bit flips easily cancel out modulo 256. CS16 performs much better (~0.7% undetected). CRC-8 outperforms CS8 by 5× (~0.4% undetected). CRC-16 is the best, catching 100% of errors (0 undetected) across all tests.
• At higher error rates (p ≥ 0.01), all frames have errors. Parity catches 100% because with errors scattered across 128 bytes, at least one byte is sure to have an odd flip. CS8 still misses about 0.3% to 0.5% due to random collisions (around 1/256). CRC-16 catches 100% of errors across all 6000 test frames.

2. Under Burst Errors (Burst Length = 8):
• Parity fails completely: Over 55% of burst errors go undetected! Because an 8-bit burst flips 8 bits in a row, it flips an even number of bits in the affected bytes, which leaves the parity check unchanged and fools the receiver.
• Checksums and CRCs catch 100% of burst errors: cs8, cs16, crc8, and crc16 caught every single burst error (0 undetected). For CRC-8 and CRC-16, this is mathematically guaranteed: any burst of length ≤ 8 is always detected by an 8-bit or 16-bit CRC.

Step 5 — (Optional) Hamming(7,4) Single-Bit Correction
We implement the Hamming(7,4) code, which encodes 4 data bits into 7 codeword bits by inserting 3 parity bits at positions 1, 2, and 4.
Figure 4.4: Hamming(7,4) Single-Bit Error Detection, Syndrome Localization, and In-Place Correction

Quick Demo Output: orig: [1, 0, 1, 1] | flip_pos: 4 | syndrome: 4 | decoded: [1, 0, 1, 1]

Single-Bit Correction vs. Double-Bit Detection: If 1 bit flips, the receiver calculates the syndrome, which directly gives the position of the flipped bit (position 4). The receiver simply flips that bit back to restore the original data. If 2 bits flip, the syndrome still flags that an error happened, but it points to the wrong bit position; trying to fix it flips a healthy bit and creates a third error. Thus, Hamming(7,4) detects two errors, but can only correct one.

2. Answers to Guiding Questions

Question 1: Give an example where parity fails but CRC-16 succeeds. Why?

Answer: If we send 00000000 with an even parity bit 0 and noise flips two bits to 11000000, the byte has two 1s. Since 2 is even, parity check passes and the error goes completely undetected. In contrast, CRC-16 succeeds because its math treats the bits as a polynomial. The generator polynomial is chosen so that no 2-bit error pattern can divide evenly into it, leaving a remainder that always flags the error.

Question 2: Why does a ones’ complement checksum sometimes miss certain multi-bit patterns?

Answer: Because checksums just add words together, order and position don't matter: (1) Cancelling errors: If one bit flips from 0 to 1 (+1) in one word, and another bit flips from 1 to 0 (-1) in a second word, the sum doesn't change. (2) Swapping words: Because A + B = B + A, changing the order of two words gives the exact same checksum. (3) Zeros: In ones' complement, all-zeros (0x0000) and all-ones (0xFFFF) both equal zero, so flipping between them doesn't change the checksum.

Question 3: How does frame length affect undetected error probability for each scheme?

Answer: (1) Parity: For random noise, longer frames have more bytes, making it more likely that at least one byte has an odd number of errors and gets caught. But for burst errors, parity remains bad (~55% undetected) no matter how long the frame is. (2) Checksums: Longer frames mean more words, so there are more ways for errors to cancel each other out. The undetected rate settles around 1/256 for 8-bit and 1/65536 for 16-bit. (3) CRCs: Short bursts (up to the CRC size) are always 100% caught, regardless of frame length. For random noise, CRC-16 catches 100% of double errors, and longer random patterns have only a tiny chance (1/2^16 ≈ 0.0015%) of slipping through.

Question 4: In practice, why do protocols combine CRC with FEC (e.g., convolutional/LDPC codes)?

Answer: They do two different, complementary jobs: (1) FEC (Forward Error Correction): Fixes common bit errors on the spot so the system doesn't have to waste time retransmitting packets, keeping speeds high. (2) CRC: Acts as a safety check. If noise is too strong and FEC fails or makes a wrong correction, CRC reliably detects the bad packet so it can be discarded and requested again. Together, FEC provides speed, while CRC guarantees data reliability.

3. Conclusion
1. In this lab, we evaluated five error-detection methods (parity, 8-bit checksum, 16-bit checksum, CRC-8, CRC-16) and one error-correcting code (Hamming(7,4)).
2. Under random bit noise (BSC), CRC-16 performed the best, catching 100% of errors with 0 undetected across all tests.
3. Under burst noise, parity failed badly (missing over 55% of errors) because 8-bit bursts flip an even number of bits in a byte.
4. Checksums and CRCs easily caught all 8-bit burst errors, with CRCs mathematically guaranteeing detection for bursts up to their size.
5. Hamming(7,4) showed how syndrome calculation can locate and correct a single bit flip without needing retransmission.
6. Real wireless systems combine FEC to fix common errors with CRC to catch any remaining bad packets.
