Mobile Constraints

1. Hardware and
screen constraints
➔

➔

➔

➔

Small screen means a high information density
trade-off, so layout and navigation depth
become critical.
Limited CPU, battery, and memory mean
response time and efﬁciency are affected by
the device, not only by the design.
Multimedia content keeps growing in size, and
with no external storage, cloud services
become necessary.
Evaluation impact: it is hard to separate a
usability problem from a performance
problem.

2. Interaction
constraints

➔ Mobile devices are used mainly in the hands (How Do Users Really
Hold Mobile Devices?).
➔ Touch targets, gestures, and grip posture affect accuracy and
speed.
➔ Multifunction buttons raise the risk of mode errors and increase
learning effort.
➔ Evaluation impact: you need to observe real posture and grip,
which desktop methods ignore.

Interaction
constraints

3. Context of use:
lab vs. ﬁeld
➔
➔
➔
➔
➔

Mobile use happens on the move, with divided attention,
interruptions, and changing environments.
Lab testing gives control and easy recording but low realism.
Field testing gives realism but is harder to control and to
record.
Some studies found ﬁeld testing revealed problems that lab
testing missed, though not in every case.
Evaluation impact: the choice of setting changes which
problems you ﬁnd.

4. Ecosystem and
connectivity constraints
➔
➔
➔
➔

Wireless operation: devices depend on network quality, so
connection drops or slow responses can break a task midway.
New apps and Internet access: users keep installing apps, and
interface conventions vary from one app to another.
Cloud dependence: with no external memory slot, storage and
content depend on the connection.
Evaluation impact: you must test under different network
conditions and across app contexts, not on one isolated app.

SMArtphone's uSability
Heuristics
(SMASH)

The gap in evaluation and the
solution
➔

Inostroza et al. (2016) reviewed the literature and found no speciﬁc usability
heuristics set for smartphones.

➔

To ﬁll this gap, they developed SMASH, a set of heuristics designed for the
constraints of smartphones: small screens, touch and hand-based
interaction, limited resources, and mobile contexts.

➔

Goal: help evaluators ﬁnd usability problems that general heuristics, like
Nielsen’s, can miss.

SMASH3: User control
and freedom

➔

The device should allow the user to undo and redo
their actions and provide clearly pointed emergency
exits to leave unwanted states. These options
should be available preferably through a physical
button or equivalent.

SMASH4: Consistency
and standards

➔ The device should follow the established
conventions, allowing the user to do
things in a familiar, standard, and
consistent way.

SMASH5: Error
prevention

➔ The device should hide or deactivate
unavailable functionalities, warn users
about critical actions, and provide access
to additional information.

SMASH6: Minimize
the user's
memory load

➔ The device should offer visible objects,
actions, and options in order to prevent
users
from
having
to
memorize
information from one part of the dialog to
another.
➔ Small screens force designers to hide
some elements, so place important
information in a visible spot.
➔ Let users select and copy instead of
retyping text.

SMASH6: Minimize
the user's
memory load

➔ In this example, the Dropbox™ application

current folder, even if the user scrolls

SMASH7:
customization and
shortcuts

➔

The device should provide basic and advanced
conﬁguration options and allow deﬁnition and
customization of shortcuts to frequent
actions.

➔

Each user has different needs, and one
standard menu or interface can’t satisfy all of
them: Let users create their own shortcuts
and customize most parts of the system, and
give them a stronger sense of ownership.

SMASH8:
Efﬁciency of use
and performance
The device should be able to load and display
the required information in a reasonable time
and minimize the required steps to perform a
task. Animations and transitions should be
displayed smoothly.
Example: After an update, the app opens on a
loading screen with a spinning icon. For more
than 30 seconds, taps do nothing, there is no
cancel button, and there is no progress
information. (Violation of the heuristic)

SMASH11: Help and
documentation

The device should provide easy-to-ﬁnd
documentation and help, centered on the
user's current task and indicating
concrete steps to follow.

SMASH12: Physical
interaction and
ergonomics
➔

The device should provide physical buttons
or the equivalent for main functionalities,
located in positions recognizable by the
user, which should ﬁt the natural posture
(and reach) of the user's dominant hand.

➔

Example: Samsung Galaxy S6 device that,
with its 5.1 in. screen, does not ﬁt the user's
palm. The circle marks the thumb's reach
area. This is a usability issue according to
this heuristic
